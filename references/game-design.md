# 从世界资料到可玩游戏

## 先决定玩家体验

用一句话明确玩家身份、近期目标、主要行动和压力来源。例如：玩家是一名港口临时信使，要在晨班前找回灯塔钥匙，可以查线索、谈判和冒险进入封锁区，潮水与巡逻会改变机会。作品的百科摘要不能代替这句体验描述。

先制作一个完整的小范围开局，再按实际需求扩展。范围应足够支持不同解法；不要给每个地点塞入无关百科，也不要预写唯一的玩家行为。

## 资料、设计与本局事实

| 层 | 内容 | 存放与更新 |
|---|---|---|
| 原作证据 | 原文明示事实、分析解释、推断及出处 | claims；修改需有资料依据，版本及剧透边界固定 |
| 改编设计 | 自定义能力数值、任务、原创地点、裁定方法 | design claims 与 gameplay；与原作事实明确区分 |
| 本局事实 | 玩家选择、损耗、NPC 状态、已发现秘密、分支偏离 | state 与事件记录；以实际裁定结果更新 |

原作里某人物将来死亡，不代表本局必须让其死亡。研究可见但当前不可用的事实放在未来时点，原作结局也不能自动成为 NPC 当前知识。用户想忠实复现时，说明哪些事件属于约束、哪些选择仍能改变局部结果。

## 世界结构

- 地点：可感知特征、可交互对象、进入条件、通往何处，以及停留的意义。
- 势力：目标、资源、矛盾和行动倾向；只保留会影响玩家选择的势力。
- 世界规律：能力代价、技术／魔法限制、社会禁忌及其证据。游戏数值转换属于设计。
- lore：每条只承载可检索的一个主题，包含常用名／别名、可用时点、可见性和知情者。
- 时间：定义 tick 与章节／集数／阶段的映射。时间推进必须有原因，追问和查看状态通常不推进时间。

任务截止应明示包含边界与否，并按最早可执行路径核算耗时。例如 tick 2 才能进入、维修花 1 阶段，完成截止须允许 tick 3。cutoff 是固定资料上限；承诺继续游玩时，为资料范围以后的本局原创阶段说明命名与推进方式。

秘密和未来信息要避免出现在公开名称、简介、开局选项、玩家角色卡和示例对白中。玩家侧资料只放当前可知内容；GM 工作材料单独管理。AI 或用户能读取全部文件的环境不能建立真正保密权限，需说明这一能力边界。

## 内置人物蒸馏

小说可从叙述、内心、行动与对白提取；影视可从场景、行为、对白及表演呈现提取。角色自己的台词与叙述者的事实陈述不能互相替代。不因一个片段就给人物固定极端性格。

NPC 最小可用画像包含：

1. 当前目标与顾虑：想要什么，害怕付出什么。
2. 情境反应：遇到威胁、请求、利益、失败、信任变化会怎样做；尽量用有证据的条件与行为。
3. 表达：长短句、称呼、直率程度、避谈主题；少量概述即可，避免抄录长段原作对白。
4. 关系：当前立场及能改变立场的事件，不把好感数字当全部人格。
5. 知识：亲眼所见、被谁告知、常识、误解、秘密分别处理。

NPC 可以主动追求目标、拒绝玩家和犯错。不要替玩家说话、决定内心、承诺行动或指定恋爱；NPC 的推测可以错误，必须保持为其观点。

NPC 自身档案会提供给该 NPC 的角色上下文，因此其 claim_ids 必须属于自身 knowledge。本人尚不知道的血统、幕后真相或失忆往事应放 gm lore；角色描述不能一边声明不知道、一边把答案写进自身内心。将条目的 available_from 设为所有支持断言中最晚的时点，或拆成不同阶段的条目，避免只删引用但留下未来内容。

## 按玩法选规则

| 玩法 | 最小闭环 | 值得记录的状态 |
|---|---|---|
| 探索／推理 | 观察→假设→调查→获得线索或代价→开放新路径 | 已发现事实、地点通行、时间、工具 |
| 社交／关系 | 诉求→表达或筹码→NPC 反应→承诺与后果 | 信任、立场、债务、承诺和知情范围 |
| 战斗／冒险 | 声明意图→说明风险→判定→伤害／位移／资源后果 | 健康、装备、敌我状态、撤退路线 |
| 经营／成长 | 分配资源→行动→产出与事件→下一周期 | 资金、时间、产能、技能和负担 |

可以组合玩法，但不要给没有战斗需求的影视社交游戏强加等级、职业和伤害系统。将实际使用的资源写入 mechanics.resources，给出范围和明确消耗；初值写入 state。脚本支持哪些变化以运行时帮助为准。

高风险的关键检定可用 mechanics.checks 绑定参数、前置条件和允许的 operations；未纳入该规则的创意行动仍由主持明示裁定。规则绑定仅检查显式 rule_id，不会从自然语言自动识别所有战斗或任务。

## 判定与失败

无风险且合理的行动直接成功；信息不足先描述可感知条件，必要时澄清行动。只有结果存在不确定性、失败有意义时才检定。检定前说明玩家可判断的风险、成本和可能结果，使用执行器真实输出，不由叙述倒推骰子。

失败可以损失时间或资源、暴露行踪、损害关系、换来不完整线索，或者改变路线。关键任务至少有替代路径；不能每次失败都原地重试，也不能让所有创意自动成功。不可逆伤害应有环境征兆和可应对机会。

脚本无法表达复杂能力互动时，以“主持裁定＋明确状态记录”实现，并如实标示。不要把未执行的模拟或未验证的随机结果包装为程序计算。

## 任务、事件与结局

任务应有可判定目标、初始状态、完成／失败条件与世界后果。用多个相互连接的情境支持不同路径；线索可以指向下一地点，失败也可换来另一条消息。玩家可以搁置任务，世界随合理时间继续变化。

把会影响后续角色反应的承诺、误解与关键经历记成带知情者的本局记忆；关系数值和记忆共同参与反应。主持先核对工具提交回执与新状态，再叙述已发生后果；失败或结果不确定时按 runtime 恢复，不提前叙述奖励或消耗。

区分已确定的世界条件与可能发生的事件。不要为了让预写桥段出现而忽略玩家行动；若玩家改变了事件前提，就更新后续分支。结束条件可以是达成目标、接受代价、撤离、失败或继续追查，不必穷举所有剧情。

## 语义检查与行为试玩

结构验证负责字段、引用和数值约束，不能判断有趣、人物合理或原作忠实。制作端须逐项读回关键证据和公开资料。

独立试玩者只获得游戏包、真实玩家请求和必要能力，不获得预期答案。观察：能否执行菜单外行动；合理失败后能否继续；NPC 是否知道未获知信息；提前追问未来事件是否被剧透；资源变化是否一致；保存后能否恢复同一状态。报告实际操作及结果，未测项目明确留空或标未执行。

试玩产生的问题按观察修复：缺通路补情境，信息泄露修归属，数值矛盾修状态变化。不因一次小问题给所有作品增加庞大规则。
